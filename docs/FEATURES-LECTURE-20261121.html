01 · 출발점 · 보드와 소프트웨어 층

칩 안에 장치는 다 있다. 문제는 그 위의 소프트웨어 층이다

  • 기능 하나를 쓰려면 층마다 조각이 맞아야 한다. 칩 안의 장치, 커널 드라이버1, 장치가 따로 받는 펌웨어2, 그리고 사용자 공간의 프로그램과 설정이다.
  • 이 보드는 Android용 BSP3의 커널에 Debian을 올렸다. 그래서 Android가 하던 몫(펌웨어 파일, 소리 경로 설정, BT 연결)을 우리가 채워야 한다.

1드라이버(driver): 운영체제가 장치를 다루게 해 주는 커널 코드. 리눅스에서는 필요할 때 끼우는 모듈(.ko)로 많이 만든다.

2펌웨어(firmware): 장치 안의 작은 프로세서가 돌리는 프로그램. 드라이버가 부팅 뒤 파일에서 읽어 장치에 넣어 준다.

3BSP(Board Support Package): 칩 회사가 주는 그 칩용 커널 · 드라이버 · 설정 묶음.

rootfs: 커널이 부팅 뒤 붙이는 기본 파일 시스템. 여기서는 Debian 12.

1Mixer: 소리 칩 안의 스위치 · 볼륨 · 경로 선택을 바꾸는 설정 값들. 이 보드에는 780개가 있다.

2ALSA: 리눅스의 기본 소리 체계. 커널 드라이버와 사용자 공간 라이브러리(alsa-lib)로 되어 있다.

① 커널 모듈

소스와 빌드 스크립트는 modules/<이름>/. vendor 소스에 고칠 점이 있으면 patch 파일로 둔다.

③ 설정 · ④ 서비스

모든 기능이 같은 세 동작을 한다. 그래서 공통 명령 e850-feature가 기능을 몰라도 부를 수 있다. 두 번 설치해도 같은 결과가 나오게(idempotent3) 썼다.

X만 따로

의존

ethernet과 desktop은 usbhost가 있어야 한다. # needs: usbhost를 쓰면 먼저 설치된다.

1sha256: 파일 내용으로 만든 64자리 지문. 한 바이트만 달라도 바뀐다.

2systemd unit: 서비스를 언제 · 어떻게 켜고 끌지 적은 파일(.service).

3Idempotent: 여러 번 해도 한 번 한 것과 결과가 같은 성질.

왜 이렇게 나눴나

  • features/: 보드에 들어가는 것. 그대로 묶어(tgz) 보낸다.
  • modules/: Mac의 Docker에서 따로 빌드하는1 커널 모듈. 결과(.ko)만 묶음에 들어간다.
  • host/: Mac에서만 도는 도구. 묶음에는 안 들어간다.

새 보드에 넣을 때

저장소를 받고, Mac에서 bundle.sh → deploy.sh. 보드1~4가 같은 커널이라 같은 묶음을 쓴다.

1Out-of-tree 빌드: 커널 소스 트리 밖의 디렉터리에서, 이미 빌드된 커널에 맞춰 모듈 하나만 빌드하는 방법(make M=…).

tgz: 여러 파일을 tar로 하나로 묶고 gzip으로 줄인 파일.

02 · 설계 · 묶음이 보드에 가는 길

Mac에서 만들고, ssh로 보내고, 보드가 제자리에 넣는다

커널 릴리스가 다르면 모듈을 넣지 않는다. 모듈은 빌드한 커널에서만 올라가기 때문이다(vermagic1). 지금 보드1~4는 모두 5.10.157-00010-g3b6b9ca51034-dirty다. 측정

1vermagic: 모듈에 적힌 "어느 커널용인가" 표시. 커널과 맞지 않으면 적재를 거부한다.

strip: 실행 파일에서 디버그 정보를 지워 크기를 줄이는 것. scsc_wlan.ko는 25 MB → 1.9 MB.

scp / ssh: 네트워크로 파일을 복사하는 / 명령을 실행하는 암호화된 방법.

02 · 설계 · 고친 모듈이 이기는 법

같은 이름의 모듈이 둘일 때, extra/가 먼저다

문제

vendor 모듈은 /lib/modules/<KVER>/에 평평하게 놓여 있다. 고친 exynos3830_sound.ko와 scsc_wlan.ko는 원래 것과 이름이 같다. 원래 파일을 덮어쓰면 되돌리기 어렵다.

방법

고친 것은 extra/에 넣고 /etc/depmod.d/e850-features.conf에 한 줄을 쓴다.

search extra built-in

depmod1가 목록(modules.dep)을 만들 때 extra를 먼저 본다. 빼려면 파일을 지우고 depmod만 다시 하면 된다.

확인 측정

$ modinfo -F filename smsc95xx
/lib/modules/5.10.157-…/extra/smsc95xx.ko
$ modinfo -F filename scsc_wlan     (보드3)
/lib/modules/5.10.157-…/extra/scsc_wlan.ko

주의: 이미 올라간 모듈은 그대로다

파일을 바꿔도 이미 적재된 모듈은 바뀌지 않는다. 그리고 이 두 모듈은 내렸다 다시 올리면 커널 패닉이 났다(05장, 07장). 그래서 고친 판은 다음 부팅부터 쓰인다.

1depmod: 모듈들이 서로 무엇을 필요로 하는지와 각 모듈 파일의 위치를 목록으로 만드는 도구. modprobe는 이 목록을 보고 모듈을 찾는다.

커널 패닉: 커널이 더 진행할 수 없는 오류를 만나 멈추는 것. 이 보드에서는 워치독이 리셋하고 fastboot로 들어간다.

03 · 시험 순서

위험한 첫 시도는 복구 수단이 있는 보드3에서, 확인된 것만 보드4로

복구 수단무엇을 하나보드3보드4
USB ACM 콘솔1네트워크가 죽어도 root 셸있음없음 (USB가 호스트 모드)
UART2커널이 죽는 순간의 로그있음없음

그래서

커널 모듈을 처음 올리는 일(소리 카드, Wi-Fi 패닉 시험, 모듈 다시 올리기)은 보드3에서 했다. 보드3에서는 패닉이 세 번 났고 모두 원격으로 살렸다. 측정

그래도 놓친 것

보드4에서 BT를 켠 채 Wi-Fi로 큰 다운로드를 하자 Wi-Fi가 끊겼다. 원격으로 살릴 길이 없어 사용자가 전원을 다시 넣어야 했다(07장).

1ACM: USB 케이블로 보드에 터미널을 여는 방식. 보드가 USB 장치(gadget)일 때만 된다.

2UART: 칩의 가장 단순한 직렬 통신 핀. 커널이 멈추기 직전까지 로그를 내보낸다.

워치독(watchdog): 정해진 시간 안에 신호가 없으면 보드를 리셋하는 타이머.

04 · USB 호스트 · 포트 하나를 두 가지로

micro-USB OTG는 평소 "장치", 켜면 "호스트"가 되어 USB-A 4개가 산다

평소(장치 모드)

Mac에 꽂으면 보드가 USB 장치가 된다. ACM 콘솔과 ECM 네트워크(192.168.7.1)가 이 길로 간다. 이때 USB-A 포트(키보드 · 마우스 · 유선랜)는 죽어 있다.

e850-usbhost on이 하는 일

  1. e850-hubpwr: LAN9514 허브1에 전원(LDO24)
  2. gpiohold.py 3 5 0: 포트 전원 GPIO2를 잡아 둔다
  3. OTG의 b_sess와 id를 0으로: 호스트 모드

끝낼 때(TERM) 거꾸로 되돌린다. 보드4의 현미경 서비스 e850-scope가 같은 일을 하고 있으면 손대지 않는다.

보드4에서 본 것 측정

$ lsusb
0424:9514  LAN9514 허브
0424:ec00  LAN9514 유선랜
04b4:00c3  현미경 카메라 (CX3)

부팅 때 켜지 않는 이유

켜는 순간 micro-USB의 ACM과 ECM이 사라진다. 원격 복구 길이 없어지므로 사용자가 고르게 했다. 계속 쓰려면 systemctl enable e850-usbhost.

1USB 허브: 포트 하나를 여러 개로 늘리는 칩. LAN9514는 허브와 유선랜이 한 칩.

2GPIO: 소프트웨어로 켜고 끄는 범용 핀. 여기서는 포트 전원 스위치.

LDO: 전압을 일정하게 내려 주는 작은 전원 회로.

04 · 유선랜 · LAN9514

드라이버 하나, 설정 파일 두 개. 그런데 MAC가 부팅마다 바뀌었다

① 드라이버

커널 소스의 drivers/net/usb/smsc95xx.c를 외부 모듈로 빌드했다. 필요한 usbnet과 MII1는 커널에 이미 들어 있었다.

② 이름 · MAC

LAN9514에 EEPROM이 없어 부팅마다 MAC2가 무작위였다. 그러면 공유기가 매번 다른 주소를 준다.

[Match] Driver=smsc95xx
[Link]  Name=eth0
        MACAddressPolicy=persistent

persistent는 machine-id로 MAC를 만든다. 보드마다 다르고 부팅마다 같다.

③ 주소

[Network] DHCP=yes
[DHCPv4]  RouteMetric=100
[Link]    RequiredForOnline=no

유선이 있으면 Wi-Fi(1024)보다 먼저 쓴다. 케이블이 없어도 부팅이 기다리지 않는다.

확인한 것 측정

보드4에서 extra/smsc95xx.ko가 올라가고, udev가 10-e850-eth.link를 적용해 이름이 eth0이 되었다.

못 한 것 미확인

케이블이 꽂혀 있지 않아(carrier 0) 링크와 DHCP 주소 받기는 확인하지 못했다.

1usbnet / MII: USB 랜 드라이버 공통 코드 / 랜 칩과 물리층 사이의 표준 접속.

2MAC 주소: 장치마다 붙는 48비트 번호. 공유기는 이것으로 기기를 구별한다.

networkd / udev: systemd의 네트워크 설정 / 장치 이름 · 권한 정하기.

05 · 오디오 · 소리가 지나가는 길

프로그램에서 헤드폰까지 다섯 블록을 지난다. 각 블록을 mixer로 이어야 한다

경로를 어디서 얻었나 소스

Android의 mixer_paths.xml에서 기본값 + route-sifs0-to-uaif0 + dev-headset 세 경로를 뽑았다. Android 전용(BD_MIXER, RDMA3) 부분은 뺐다. mixer-path.py가 이것을 amixer -s 입력으로 바꾼다.

부팅 때

e850-audio.service가 모듈을 올려 ABOX DSP1에 펌웨어를 넣고, 카드가 생기면 경로를 설정한다. 그 뒤로는 aplay 같은 보통 ALSA 프로그램이 그대로 쓴다.

1DSP: 신호 처리(소리 섞기, 표본률 바꾸기)에 특화된 프로세서. ABOX는 Exynos 안의 오디오 DSP 블록이다.

RDMA: 메모리에 있는 소리 데이터를 읽어 오는 DMA 통로. I2S: 칩끼리 디지털 소리를 주고받는 직렬 규격. DAC: 디지털 소리를 전압으로 바꾸는 회로.

DAPM: 쓰는 경로의 블록만 전원을 켜는 ASoC의 절전 체계. 경로가 이어졌는지 보는 데도 쓴다.

05 · 오디오 · 카드가 생기지 않은 이유

드라이버는 DT 자식 노드를 "순서"로 읽는데, 순서가 뒤집혀 있었다

증상 측정

ABOX 펌웨어는 "Calliope is ready to sing"까지 갔다. 그런데 카드 등록이 실패했다.

No CPU DAIs support playback for stream UAIF0
can't create pcm UAIF0 :-22

원인 소스

exynos3830_sound.c는 sound 노드의 자식을 정적 배열 exynos_dai[](rdma0~11, wdma0~4, …, uaif0~2, …)에 위치로 맞춘다. 그런데 부트 이미지를 만들 때 fdtoverlay1가 overlay의 새 자식들을 거꾸로 넣었다(merged.dtb에서 0번 fwd … 62번 rdma0). 그래서 SIFS2 같은 링크가 UAIF0 자리에 들어갔다.

수정: 이름으로 정렬한 뒤 맞춘다

modules/exynos3830-sound/exynos3830-sound-order.patch는 자식을 이름(접두어, 번호, _be)으로 정렬한 다음 배열에 맞춘다. DT는 그대로 두었다. 다른 보드의 DT도 고칠 필요가 없다.

결과 측정

깨끗한 부팅에서 패치한 모듈을 올리자 card0 ExynosMadera가 생겼다. 재생 장치 RDMA0~11과 calliope_0, 컨트롤 780개.

교훈

"순서에 기대는 코드"는 도구가 바뀌면 조용히 틀린다. 오류 메시지는 UAIF0을 가리켰지만 원인은 DT를 합치는 도구에 있었다.

1fdtoverlay: 기본 DT(SoC)에 보드용 DT 조각(overlay)을 덧붙여 DT 하나로 합치는 도구.

DAI(Digital Audio Interface): 소리 데이터가 드나드는 디지털 접속점 하나. ASoC는 CPU 쪽 DAI와 코덱 쪽 DAI를 짝지어 "링크"를 만든다.

machine 드라이버: 한 보드에서 어느 DAI를 어느 코덱에 이을지 정하는 ASoC 드라이버. 여기서는 exynos3830_sound.

05 · 오디오 · 결과와 함정

재생 시간은 맞다. 그러나 한 번에 한 프로그램, 48 kHz로만

보드장치입력3초 분량 재생
보드3hw:0,048 kHz WAV3.193 s
보드4default44.1 kHz (변환 전)2.56 s
보드4default44.1 kHz (48k로 변환)3.33 s
보드4default48 kHz3.19 s

44.1 kHz를 그대로 넣으면 약 15% 빨리 끝났다. 장치는 8~384 kHz를 다 받는다고 알리지만 실제로는 48 kHz로 돈다. 그래서 asound.conf의 plug1가 늘 48 kHz S16 2채널로 바꾼다. 측정 귀로는 미확인

dmix가 안 된다

여러 프로그램의 소리를 섞는 ALSA dmix2는 SysV IPC 세마포어를 쓴다. 이 커널은 CONFIG_SYSVIPC가 꺼져 있어 "Function not implemented"가 났다. 그래서 한 번에 한 프로그램만 소리를 낸다.

패닉: 같은 부팅에서 다시 올리기

등록에 실패한 같은 부팅에서 원래 모듈을 내리고 패치 모듈을 올리자 커널 패닉(__list_add_valid BUG)이 났다. 그래서 audio.sh는 카드 없이 모듈만 있으면 다시 시도하지 않고 "재부팅하라"고만 한다.

권한

philip이 audio 그룹에 없어 장치를 열지 못했다. 설치할 때 일반 사용자(uid 1000~59999)를 그룹에 넣는다.

1plug: ALSA의 자동 변환 층. 프로그램이 주는 형식(표본률, 채널, 비트)을 장치가 받는 형식으로 바꾼다.

2dmix: 여러 프로그램의 소리를 사용자 공간에서 섞어 장치 하나로 보내는 ALSA 플러그인. 프로세스끼리 공유 메모리와 세마포어로 맞춘다.

SysV IPC: 프로세스끼리 공유 메모리 · 세마포어 · 메시지 큐를 쓰는 오래된 유닉스 방식.

06 · 영상 코덱 MFC

장치는 생겼다. 그러나 ffmpeg가 쓰는 버퍼 방식을 받지 않는다

넣은 것

  • /lib/firmware/mfc_fw.bin (Linaro의 mfc_fw_v10.21.bin을 드라이버가 찾는 이름으로)
  • e850-mfc.service: 부팅 때 modprobe exynos_mfc
  • 부팅 경합을 고친 exynos_mfc.ko(07장 끝)
  • 사용자를 video 그룹에

생긴 장치 측정

/dev/video7  s5p-mfc-enc   인코더
/dev/video8, 9             secure 판 (안 씀)

보드3 · 보드4 둘 다. 열기도 된다(보드3).

V4L2 M2M

MFC는 V4L2 mem2mem1 장치다. 압축된 H.264를 한 버퍼에 넣으면 풀린 화면이 다른 버퍼로 나온다. ffmpeg의 h264_v4l2m2m이 이 길을 쓴다.

ffmpeg로 풀기: 실패 측정

  • ffmpeg가 secure 노드(video8)를 먼저 골랐다. 막으니 video6을 골랐다.
  • 그래도 버퍼 요청이 EINVAL. 드라이버가 MMAP2을 "Not supported"로 거부한다(DMABUF · USERPTR만). ffmpeg는 MMAP만 쓴다.
  • CPU로는 1080p 10초 분량을 0.76초에 푼다(시험 영상).

1V4L2 mem2mem: 리눅스 영상 장치 규격(V4L2) 가운데, 메모리에서 받아 처리하고 다시 메모리로 내보내는 장치(코덱, 크기 변환기) 방식.

MFC(Multi-Format Codec): Exynos의 하드웨어 영상 압축 · 풀기 블록. H.264, HEVC 등을 CPU 대신 처리한다.

2MMAP / DMABUF: 드라이버가 버퍼를 빌려주는 방식 / 남이 만든 버퍼를 넘겨받는 방식(Android).

07 · Bluetooth · 사용자 공간 브리지

vendor의 연결부가 빌드되지 않아, 파이썬 프로그램 하나로 BlueZ에 이었다

왜 브리지인가 소스

커널 안의 scsc_bluez.c는 빌드되지 않는다. 없는 헤더(wakelock.h), 두 번째 module_init, 커널 버퍼를 사용자 함수에 넘기는 코드가 있다.

첫 실패와 고침

vhci가 1초 뒤 hci0을 스스로 만들기를 기다렸더니, 그 전에 칩의 이벤트가 와서 write가 ENODEV1로 실패했다. vhci에 ff 00을 먼저 써서 hci0을 바로 만들게 했다.

결과 측정

보드3: hci0 UP RUNNING, 12초 스캔에 27대. 보드4: 23대. 스캔하는 동안 Wi-Fi 복구 0번, ping 손실 0.

1ENODEV: "그런 장치가 없다"는 리눅스 오류 번호. 여기서는 hci0이 아직 만들어지지 않았다는 뜻.

H4: BT 칩과 호스트가 주고받는 가장 단순한 형식. 바이트 하나로 종류(명령 · 데이터 · 이벤트)를 알리고 헤더에 길이가 있다.

vhci: 사용자 프로그램이 가짜 BT 장치를 만들게 해 주는 커널 드라이버. BlueZ는 진짜 칩과 구별하지 않는다.

07 · 사고 · 보드4가 사라졌다

BT를 켠 채 큰 다운로드를 하자 보드4가 Wi-Fi에서 사라졌다. 보드3에서 재현했다

보드4에서 일어난 일 측정

  1. e850-bt.service가 켜진 상태
  2. desktop 패키지 278개를 Wi-Fi로 받아 설치. 마지막 줄까지 정상(rc=0)
  3. 직후 Wi-Fi에서 사라짐(ARP incomplete)
  4. USB는 호스트 모드, 유선 케이블 없음 → 원격으로 살릴 길 없음
  5. 사용자가 전원을 다시 넣음. 부팅은 되지만 무선이 안 됨

첫 가설 (뒤에 뒤집힘)

Wi-Fi 펌웨어(WLBT)는 원래 가끔 패닉1하고, 드라이버가 6초쯤 뒤 되살린다(11.31). BT가 열려 있을 때 그 되살리기가 실패하는 것 아닐까. 이 가설로 실제 버그를 하나 찾았지만, 보드4의 원인은 따로 있었다(07장 끝).

재현(보드3): BT 브리지를 켠 채 강제 패닉

scsc_mx_service_open: error: refused due to
    previous f/w failure
slsi_chip_recovery: fail at line:7644   (WARNING)
slsi_net_open: Fail: called when MLME in
    blocked state

Wi-Fi가 40초 안에 돌아오지 않았고 /proc/driver/mxman_ctrl0도 사라졌다. BT를 끄고 하면 늘 돌아왔다.

살리는 방법도 없다

rmmod scsc_wlan; modprobe scsc_wlan은 커널 패닉(mxman_wifi_kobject_ref_get). 이 상태는 재부팅으로만 풀린다. 보드3은 워치독 → fastboot → fastboot reboot로 살렸다.

1펌웨어 패닉: 칩 안의 펌웨어가 스스로 오류를 감지하고 멈추는 것. 드라이버가 알아채고 펌웨어를 다시 올린다(복구).

MLME: Wi-Fi 드라이버에서 연결 · 해제 같은 관리 동작을 맡는 부분. "blocked"면 복구가 끝나지 않아 막힌 상태다.

ARP incomplete: 그 IP에 대한 MAC 주소 응답이 없다는 뜻. 그 기기가 망에 없다.

07 · 원인 · 두 작업의 경주

복구 작업이 "열기 금지"가 풀리기 전에 서비스를 열고, 다시 시도하지 않았다

두 작업은 서로 다른 작업 큐1에서 돈다. 근거는 vendor 소스(mxman.c, mgt.c)를 읽은 것과 보드3 로그의 순서다. 소스 측정 BT remove가 왜 꼭 그만큼 늦는지는 재지 않았다.

1작업 큐(workqueue): 커널이 나중에 할 일을 넣어 두는 줄. 줄이 다르면 서로 순서가 보장되지 않는다.

경쟁 조건(race condition): 두 작업의 순서에 따라 결과가 달라지는 버그. 보통은 운 좋게 맞는 순서로 돌아 숨어 있다.

remove / probe: 드라이버가 장치를 놓는 / 다시 잡는 함수. 펌웨어 복구 때 모든 드라이버가 이 둘을 거친다.

07 · 수정 · 다시 시도하기

열기에 실패하면 100 ms마다 최대 50번 다시 연다

/* mgt.c, slsi_chip_recovery() */
-  SLSI_EC_GOTO(slsi_sm_wlan_service_open(sdev),
-               err, err_done);
+  /* mxman_failure_work forbids service start until
+   * every client is reset; with BT open that ends
+   * after we get here, so retry a while. */
+  for (i = 0; i < 50; i++) {
+      err = slsi_sm_wlan_service_open(sdev);
+      if (!err)
+          break;
+      SLSI_INFO(sdev, "service open failed (%d)"
+                " during recovery, retry %d\n",
+                err, i + 1);
+      msleep(100);
+  }
+  if (err)
+      goto err_done;

실패한 첫 판

거부의 오류 번호 -EILSEQ1일 때만 다시 시도했다. 그런데 slsi_sm_wlan_service_open이 그것을 -EINVAL로 바꿔 돌려준다. 그래서 아무 일도 하지 않았다. 지금 판은 어떤 오류든 다시 시도한다. 실패한 열기는 상태를 PROBED로 되돌리므로 다시 열어도 된다. 소스

보드3, 강제 패닉결과Wi-Fi 복귀
원래 모듈, BT 켬안 돌아옴—
고친 모듈, BT 켬거부 1번, retry 1에서 성공8,094 ms
고친 모듈, BT 끔WARNING 08,139 ms

BT 브리지는 복구 때 끝나고 5초 뒤 다시 뜬다(hci0 UP, 스캔 17대). 측정

1-EINVAL / -EILSEQ: 커널 함수가 돌려주는 음수 오류 번호("잘못된 인자", "잘못된 순서").

msleep: 커널 코드가 밀리초 동안 잠드는 함수.

패치: 고친 차이만 적은 파일. -는 지운 줄, +는 넣은 줄.

07 · 진짜 원인 · 로그인하면 커널이 죽었다

X를 켜자 보드3이 죽었고, 그 뒤로는 부팅할 때마다 35초에 죽었다

UART에 남은 것 측정

Internal error: BRK handler: f2005512
pc : freqboost_can_attach+0x1bc [ems]
 cpu_cgroup_can_attach ← cgroup_attach_task
 ← cgroup_procs_write      (Comm: systemd, PID 1)
Kernel panic - not syncing

0x5512는 UBSAN1의 "배열 범위 초과" 함정이다. systemd가 프로세스를 cgroup2에 넣는 순간 vendor 스케줄러 모듈 ems가 죽었다.

소스 소스

dst_bg = css->id - 1;          /* cgroup 번호 */
bg->group[dst_bg].tasks += 1;  /* 배열 크기 9 */

Android의 cpu cgroup 9개만 생각한 코드다.

왜 이제야

  1. 기본 rootfs에는 libpam-systemd가 없다. 로그인해도 세션이 안 생기고 cpu 컨트롤러가 꺼져 있다(보드1 확인).
  2. desktop 패키지가 dbus-user-session → libpam-systemd를 들였다.
  3. 이제 로그인마다 user@UID.service가 생기고 cpu를 위임받는다. 사용자 slice들이 CPUWeight를 켜서 cpu cgroup이 9개를 넘는다.

보드4는?

같은 패키지를 설치한 직후 사라졌다. 다음 로그인에서 패닉 → 워치독 → fastboot에서 멈춤 → Wi-Fi에서 사라짐. 이것일 가능성이 크다. 보드4 로그로 미확인

1UBSAN: 배열 범위 초과 같은 잘못을 실행 중에 잡는 컴파일러 검사. 이 커널은 잡으면 멈춘다.

2cgroup: 프로세스를 묶어 CPU · 메모리를 나누는 커널 기능. systemd가 서비스 · 로그인마다 만든다.

PAM / logind: 로그인 절차 모듈 / 로그인 세션 관리 서비스.

07 · 수정 · cpu 컨트롤러를 끈다

두 겹으로 막았다: 커널 명령줄과 systemd 설정

① 부트 명령줄 cgroup_disable=cpu1

cpu 컨트롤러가 꺼지면 모든 태스크가 루트(id 1)에 있어 EMS 번호가 늘 0이다. 이 시스템은 cgroup CPU 가중치를 쓰지 않는다.

build-bootimg.sh에 넣었고, 지금 이미지(boot-dvs3)에는 DTB의 bootargs만 고친 판을 만들었다.

② desktop 설치가 apt 전에

# /etc/systemd/system/user@.service.d/
#   e850-no-cpu-delegate.conf
[Service]
Delegate=
Delegate=pids memory

새 이미지를 굽지 않은 보드용. 컨테이너 시험: 로그인 하나에 cpu cgroup 13개 → 1개. 측정

실수: fastboot boot

굽지 않고 RAM으로 띄우려 했다. 이 LK에서는 안 된다는 것이 기록 7.3절에 이미 있었다. LK가 멈춰 보드3 전원을 다시 넣어야 했다. 기록을 먼저 찾아봤어야 했다.

교훈

  • 패키지 하나(libpam-systemd)가 커널의 숨은 가정을 깨울 수 있다.
  • 그럴듯한 첫 가설로 실제 버그를 찾았어도, 그것이 그 사고의 원인이라는 보장은 없다. 사고 보드의 로그(/proc/last_kmsg)가 먼저다.

1cgroup_disable=: 부팅 때 지정한 cgroup 컨트롤러를 아예 끄는 커널 인자.

Delegate=: systemd가 서비스에게 cgroup 컨트롤러 관리를 넘겨주는 설정. 빈 값으로 목록을 지운 뒤 다시 쓴다.

drop-in: 원래 unit 파일을 고치지 않고 덧붙이는 설정 조각(*.service.d/*.conf).

07 · 보드에서 확인 · 그다음 숨은 버그

cpu 패닉은 사라졌고, 그 뒤에 부팅 중 MFC 패닉이 드러났다

보드3, 고친 이미지 측정

cmdline      … cgroup_disable=cpu
controllers  cpuset io memory     # cpu 없음
세션 2개, user@0 active → 패닉 0  # 전엔 35초마다

새 패닉 측정

  1. 23.46 s, MFC가 /dev/video6을 만든다
  2. 3 ms 뒤 udev1의 v4l_id가 연다
  3. no mfc device to run인데 열기는 "성공"
  4. 닫을 때 mfc_release가 빈 주소를 읽어 Oops

소스와 한 줄 수정

video_register_device(vfd, …); /* 노드 생김 */
                    /* 여기서 열면 dev == NULL */
video_set_drvdata(vfd, dev);

mfc_open():  if (!dev) {
+                ret = -ENODEV;   /* 전엔 0 */
                 goto err_no_device; }

실패한 열기에는 release가 불리지 않는다. 부팅 세 번 중 두 번 경합이 났고, 고친 판은 두 번 다 견뎠다.

MFC는 내리지 않는다

열고 있는 중에 rmmod하면 패닉, 다시 올리면 코어가 안 붙는다. 바꾼 모듈은 재부팅으로 쓴다.

1udev / v4l_id: 장치가 생기면 규칙을 실행하는 관리자 / 영상 장치를 열어 종류를 묻는 udev 도구.

drvdata: 장치에 붙여 두는 드라이버 자신의 자료 포인터. 열기 함수가 이것으로 장치를 찾는다.

Oops: 커널이 잘못된 메모리를 읽는 등 스스로 복구 못 할 오류. 이 커널은 곧 패닉한다.

08 · 정리 · 다른 보드에 넣기

저장소만 있으면 어느 보드든 같은 세 줄이다

# Mac (저장소 루트, Docker Desktop 켜 둠)
sh features/host/bundle.sh
    # → out/e850-features.tgz (모듈 빌드 + 펌웨어 확인)
sh features/host/deploy.sh1 philip@<보드 IP> \
    ethernet audio video bt       # X 없이 가볍게
sh features/host/deploy.sh philip@<보드 IP> desktop

# 보드
e850-feature status
sudo systemctl reboot     # bt를 처음 넣었으면 한 번

bt를 처음 넣은 보드는 재부팅 한 번

고친 scsc_wlan.ko는 다음 부팅부터 쓰인다(다시 올리면 패닉). 그 전에는 bt-check.sh가 BT를 켜지 않는다. 원래 모듈에 BT를 켜면 07장의 사고가 다시 난다.

새 기능을 만들 때

  1. features/<이름>/feature.sh: 맨 위에 # about:(와 # needs:), install | remove | status
  2. . "$ROOT/common.sh"로 ko_install, unit_install, apt_need를 쓴다
  3. 새 모듈은 modules/<이름>/build-module.sh, 그리고 bundle.sh의 MODS에
  4. 펌웨어는 fetch-fw.py의 FILES에. fw.sha256에 지문이 더해진다

커널을 바꾸면

KVER이 달라져 모듈 설치가 거부된다. 새 커널로 bundle.sh를 다시 돌리면 된다. 소스 패치는 그대로 쓰인다.

1deploy.sh: 묶음을 scp로 보드의 /var/tmp에 보내고, ssh로 sudo e850-feature install …을 실행하는 Mac 스크립트. 보드의 sudo 비밀번호는 사람이 친다.

KVER: 묶음을 만들 때 쓴 커널 릴리스 문자열. 보드의 uname -r과 같아야 한다.

08 · 정리 · 배운 것과 남은 일

vendor 코드의 숨은 가정들이 이번 작업의 대부분이었다

배운 것

  • 순서에 기대는 코드: vendor 소리 드라이버1는 DT 자식의 위치를 믿었다. DT 합치는 도구가 순서를 바꾸자 조용히 틀렸다.
  • Android에서만 맞는 순서: Wi-Fi 복구는 BT 사용자가 늘 빨리 닫는다고 가정했다. Debian의 브리지는 그렇지 않았다.
  • 다시 올리기는 안전하지 않다: 두 모듈 모두 rmmod 뒤 다시 올리면 패닉. 그래서 "다음 부팅부터"를 설계에 넣었다.
  • Android의 cgroup 수: 스케줄러 모듈 ems는 cpu cgroup이 9개뿐이라고 믿었다. 패키지 하나가 그 가정을 깼다.
  • 복구 길이 먼저: 보드4는 원격 복구 수단이 없었고, 보드3은 usbhost가 root 셸을 끊었다.

남은 일

  1. 보드4: USB 케이블로 같은 이미지, last_kmsg로 원인 확인, 고친 묶음 배포
  2. MFC를 DMABUF로 쓰는 클라이언트(필요하면)
  3. 헤드폰, 유선랜
  4. 보드1 · 보드2에도 X 없이 설치
